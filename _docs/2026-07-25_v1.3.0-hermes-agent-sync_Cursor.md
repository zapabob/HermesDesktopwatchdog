# 2026-07-25 v1.3.0 hermes-agent sync — Cursor

## 概要

セマンティックバージョンを **v1.2.0 → v1.3.0** に上げ、`zapabob/hermes-agent` の `scripts/windows/watchdog-go` を再 diff。
v1.2.0 以降に hermes-agent 側で入った **新規コミット `979093d33a fix(watchdog-go): stop killing managed serve and reuse session tokens`** 由来の
高価値 additive 変更を移植し、multi-platform `tar.gz` Release・GH Pages・README を更新した。

**「新デルタ無し」ではない。** hermes-agent 側 `backend.go` / `process_windows.go` は 2026-07-25 に更新されており、
セッショントークン継続性という実運用上重要なギャップが残っていた。

## 背景・要求

- 本リポが canonical（hermes-agent は READ ONLY、一切編集しない）
- P1–P6（state machine / heartbeat / IPC / warm-start / Job Object / update suppress）を壊さない
- v1.1.0 / v1.2.0 で取り込み済みの `--skip-build`・auth-drift・netstat fallback・bounded taskkill・async prewarm を維持
- hot-swap deadlock 修正（`bm.mu` を遅い処理中に握らない）を退行させない
- 単純な hermes-agent 版 `watchdog.go` / `server.go` / `findHealthyDesktopBackend` で上書きしない

## 適用 SOP / Skill

- Implementation Start Gate / MILSPEC Codex Standard / SOP-Go

## 前提・判断（CoT）

1. **リリース前状態の確認**: `git status` はクリーン（未追跡の作業ログのみ）。
   ただし **ローカル/リモートの `v1.2.0` タグが `v1.1.0` と同じ commit `4415d5f` を指す誤タグ**であることを検出。
   実際の v1.2.0 実装 `0ebda04` と検証ログ `208920f` はタグ範囲外だった。→ v1.3.0 は新 HEAD にタグ付けして解消する。
2. **hermes-agent 再 diff**: `backend.go` +158/-113、`process_windows.go` はローカルが分割済み（`process_common.go` / `health.go`）のため見かけ上の差分は大きいが、
   実質ギャップは 6 点に絞られた。
3. **上書き禁止の判定**: `findHealthyDesktopBackend` の Ready/Live 段階プローブ、`probeBackendHealth` / `quickBackendReady`、
   Job Object、`DefaultManagedBackendPort = 9118`（9119 は本リポの予約 ops ポート）は **本リポが優位**なので維持。
4. **ロック方針**: hermes-agent 版は `EnsureHealthy` 全体を `bm.mu` で直列化しており、そのまま取り込むと hot-swap deadlock 修正が壊れる。
   → 専用の `spawnMu` を追加して「直列化」と「`/api/status` 応答性」を両立させた（v1.2.0 の残留リスクだった prewarm∥RunLoop の race も解消）。
5. **PID backfill の netstat はロック外**で実行し、`netstatQuickTimeout = 2s` に制限。ロック保持時間を伸ばさない。

## 実装詳細

### hermes-agent から merge したもの

| # | Item | Source | なぜ重要か |
|---|------|--------|-----------|
| M1 | `buildServeCommand(cfg, preferredToken)` — セッショントークン再利用 | backend.go | 生存中の Desktop は起動時の `HERMES_DESKTOP_REMOTE_TOKEN` を保持し続ける。backend flap のたびに新規 mint すると Desktop 再起動まで gated API が 401 |
| M2 | `stopLocked()` が `bm.token` を保持 | backend.go | M1 の前提。drift replace 経路だけ明示的にクリア |
| M3 | `currentHealthy` 経路で manifest token を優先 | backend.go | in-memory が古いだけの正常 serve を kill しない |
| M4 | `waitManagedPortCleared(port, timeout, logger)` | process_windows.go | kill→確認ループ。旧 `stopListenersOnPort + sleep 1s` は wedged occupant と race して token-drift ループを誘発 |
| M5 | `netstatTCPOutput(timeout)` — bounded netstat | process_windows.go | 従来は `exec.Command(...).Output()` で無制限。TCP スタックが刺さると probe ループごと停止 |
| M6 | orphan reap: managed port が healthy なら reap 全スキップ + listener PID を skip 集合へ | process_windows.go | 非 listening な python/hermes wrapper を `taskkill /T` すると :9118 を持つ子まで落ち、Desktop ECONNRESET → DOWN → relaunch ループ |
| M7 | manifest の `url` エイリアス + `updatedAt` を `json.RawMessage` 化 | backend.go | Desktop / operator ツールも同ファイルを書く。厳格スキーマだと manifest 全体が読めなくなる |
| M8 | `publishManifestLocked` の PID backfill | backend.go | pid 不明時に netstat で補完（ロック外・2s 上限で実施） |

### 本リポ独自に上乗せしたもの（hermes-agent より厳しい側）

- **`spawnMu`** — `EnsureHealthy` 全体を直列化しつつ `bm.mu` は短時間しか握らない。`/api/status`（`JobSnapshot`）が cold start 中もブロックしない
- orphan reap の「listening ports 不明なら reap しない」ガードを維持（hermes-agent は削除済み＝より危険）
- auth 失敗トークンは `bm.token = ""` で明示破棄し、次回 spawn の preferred に持ち越さない

### 意図的に上書きしなかったもの

| 項目 | 理由 |
|------|------|
| `watchdog.go` / `server.go` | 本リポの P1–P6 実装が hermes-agent より大きく、上位互換 |
| `findHealthyDesktopBackend` の Live/Ready 段階プローブ | 本リポ優位（hermes-agent は `testBackendStatus` 単段） |
| `DefaultManagedBackendPort = 9119` | 本リポは 9119 を予約 ops ポート扱い。9118 を維持 |
| `EnsureHealthy` 全体の `bm.mu` 直列化 | hot-swap deadlock 修正を壊す。`spawnMu` で代替 |
| hermes-agent のネスト layout パス解決 | 本リポは standalone |

## 残留リスク

- **C: 空き容量が慢性的に逼迫**（作業後も約 1.2 GB）。Go キャッシュを E: に逃がしているのは本セッションのシェル環境変数のみで、
  次回セッションでは再び C: を使う。恒久対応するなら `setx GOCACHE E:\go-build-cache` を推奨。
- **ローカル `v1.2.0` タグは誤って `4415d5f`（= v1.1.0 commit）を指したまま**。v1.3.0 は正しい HEAD にタグ付けしたが、
  過去タグの付け替えは既存 clone を壊すため実施していない。
- セッショントークン再利用は「Desktop が生きている限り旧トークンが有効」という hermes serve 側の前提に依存する。
  serve 側がトークンを拒否した場合は従来どおり drift replace + 新規 mint にフォールバックする。
- `waitManagedPortCleared` は最大 15s ブロックする。`EnsureHealthy` 内から呼ばれるが `spawnMu` のみ保持のため `/api/status` は影響を受けない。
- Linux/macOS は依然としてスタブのみ。本番 Desktop 監視に使ってはいけない。
- GitHub Pages 反映に数分の遅延がありうる。

## 次の推奨アクション

- `setx GOCACHE E:\go-build-cache` などで恒久的にビルドキャッシュを空きのあるドライブへ
- Desktop 側と組み合わせた長時間ソークで、backend flap 後に `/api/sessions` が 401 に落ちないことを実測
- CI で `Package-Release.ps1` とクロスビルドを自動化（ローカルディスク依存の解消）
